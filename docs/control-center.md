# FitLog Control Center

FitLog Control Center — однопользовательский web-интерфейс к данным FitLog. Этот документ описывает локальный запуск и целевую архитектуру. Он не подтверждает, что Control Center уже развёрнут в production.

## Архитектура

- Next.js-приложение находится в `web/` и обращается к same-origin API по префиксу `/api/v1`.
- В локальном режиме Next проксирует `/api/*` в Go-сервис на `http://localhost:8080`; внутренний адрес можно переопределить через `FITLOG_API_INTERNAL_URL`.
- Go-сервис отвечает за авторизацию, валидацию, timezone-aware диапазоны, аналитику, импорт и доступ к PostgreSQL. Frontend не вычисляет итоговые метрики из полного набора сырых записей.
- Workspace однопользовательский. `FITLOG_DASHBOARD_OWNER_ID` задаёт владельца явно; если он не указан, используется первый корректный ID из `TELEGRAM_ALLOWED_USER_IDS`.

## Доступ и безопасность

`FITLOG_DASHBOARD_TOKEN` — опциональный секрет включения Control Center. При пустом значении существующие bot/OAuth-сценарии продолжают работать, а `/api/v1` остаётся недоступным для dashboard. Токен должен быть случайным, храниться только в секретах окружения и не попадать в Git, `NEXT_PUBLIC_*`, логи или клиентскую сборку.

`POST /api/v1/auth/session` принимает токен в JSON, сравнивает его SHA-256 digest в constant time и при успехе устанавливает cookie `fitlog_dashboard_session`. Cookie содержит версию, owner ID, срок действия и HMAC-SHA256-подпись ключом, производным от dashboard token; исходный токен в cookie не сохраняется. Срок сессии — 30 дней, `Path=/`, `HttpOnly`, `SameSite=Strict`. `Secure` включается для TLS-запроса либо при `X-Forwarded-Proto: https`; локальный HTTP остаётся работоспособным без `Secure`.

`GET /api/v1/auth/session` возвращает статус сессии. `DELETE /api/v1/auth/session` завершает действующую сессию и очищает cookie. Клиент отправляет cookie с `credentials: include`; токен не следует сохранять в `localStorage`. Для logout и всех остальных авторизованных изменяющих `POST`/`PUT`/`DELETE` запросов frontend добавляет точный заголовок:

```text
X-Fitlog-Request: 1
```

Backend проверяет этот заголовок вместе с подписанной сессией. Сам по себе заголовок не является авторизацией. Caddy не должен удалять cookie, `X-Fitlog-Request` или корректный `X-Forwarded-Proto`.

Если `FITLOG_DASHBOARD_TOKEN` пуст, session endpoints и защищённый API отвечают `503` с кодом `dashboard_disabled`. Это защита персонального single-user workspace, а не полноценная multi-user IAM/RBAC-система. Замена dashboard token меняет ключ подписи и тем самым инвалидирует ранее выданные cookie.

## Локальный запуск

Нужны PostgreSQL, настроенный локальный `.env`, Go и Node.js с установленными зависимостями `web/`.

Применить миграции:

```bash
make migrate-up
```

Запустить Go backend:

```bash
make run
```

В другом терминале запустить frontend:

```bash
npm --prefix web run dev
```

По умолчанию backend слушает `:8080`, а Next dev server — свой стандартный локальный порт. Браузер должен открывать Next-приложение; запросы `/api/v1/*` пройдут через его rewrite в Go.

### Demo seed

Демонстрационные данные создаются только отдельной явной командой после миграций:

```bash
go run ./cmd/fitlog demo-seed
```

Seed детерминирован и предназначен для локальной разработки/демонстрации. Не добавляйте его в startup, миграции или production-процедуру и не запускайте на базе с реальными данными без отдельной проверки и резервной копии.

### Ручной backfill FatSecret

Команда использует сохранённую в `oauth_tokens` делегированную пару OAuth 1.0
access token/secret (с fallback на legacy env), запрашивает дневные итоги
помесячно и по умолчанию охватывает последние 100 полностью завершённых дней:

```bash
go run ./cmd/fitlog fatsecret-backfill --days 100 --dry-run
go run ./cmd/fitlog fatsecret-backfill --from 2026-05-13 --to 2026-08-20 --dry-run
```

Перед записью весь диапазон успешно загружается целиком. Затем строки
`source=fatsecret`, `external_id=sync:day:<date_int>` обновляются одной
owner-scoped транзакцией; manual/file-import строки не затрагиваются. Повторный
запуск обновляет исправленные дни и не создаёт дубликаты. Отсутствующие в ответе
дни не удаляются автоматически из-за возможного лага провайдера. Месячный API
даёт только калории и Б/Ж/У, поэтому клетчатка, сахар, натрий, калий и вода
остаются `null`, а не нулями.

Официальные правила FatSecret разрешают большинство значений дневника хранить
только как кэш до 24 часов. Постоянная запись специально требует явного флага и
допустима лишь при наличии отдельного права на хранение:

```bash
go run ./cmd/fitlog fatsecret-backfill --days 100 --storage-authorized
```

Без такого права используйте пользовательский CSV export FatSecret и обычный
Data Imports. Справка: [Storable Data](https://platform.fatsecret.com/docs/guides/storable-data)
и [Food Diary export](https://www.fatsecret.com/fatsecret-app-help/reports-page/use-export-or-print-function).

### InBody из фитнес-клуба

На странице Body можно сохранить обычный результат InBody вручную или через
CSV/JSON. Помимо веса, процента/массы жира и скелетной мышечной массы,
поддерживаются TBW, ICW, ECW, ECW/TBW, белковая и минеральная масса, BMI,
уровень и площадь висцерального жира, BMR, InBody Score и фазовый угол. Для
левой/правой руки, корпуса и левой/правой ноги сохраняются segmental lean/fat
mass и percent.

После сохранения интерфейс показывает:

- изменение жировой и безжировой массы относительно предыдущего замера;
- динамику мышц, воды, висцерального жира, BMR, score и фазового угла;
- TBW/ICW/ECW и справочный контекст ECW/TBW;
- левую/правую разницу сегментарной lean mass.

Проценты сегментов не ограничиваются 100: на листах InBody это может быть
отношение к референсу, а не доля массы. Для сопоставимости тренда делайте замеры
в похожих условиях гидратации, времени суток и нагрузки. Справочные границы в
интерфейсе дают контекст по материалам производителя и не являются диагнозом:
[разбор листа результатов](https://research.inbody.com/result-sheet-interpretation/).

Для file import используются те же общие имена полей и плоские сегментарные
ключи, например `total_body_water_l`, `ecw_tbw_ratio`,
`left_arm_lean_mass_kg`, `right_leg_fat_percent`. Алиасы `TBW`, `ICW`, `ECW`,
`ECW/TBW`, `BMR`, `VFA` и `phase_angle` распознаются при preview. Стабильный
`external_id` с листа/экспорта делает повторный импорт идемпотентным.

## Диапазоны дат и missing data

- `from` и `to` — включительные календарные даты в IANA timezone пользователя.
- На backend диапазон следует преобразовывать в полуинтервал: начало `from` включительно и начало дня после `to` исключительно. Это сохраняет календарную семантику на переходах DST.
- Максимальная длина запроса — 366 дней с учётом обеих границ. Перевёрнутые, некорректные и более длинные диапазоны отклоняются валидацией.
- Сравниваемый период должен иметь ту же календарную длину и непосредственно предшествовать основному диапазону.
- Отсутствующее измерение хранится и передаётся как `null`/missing, а не как числовой ноль. Графики должны оставлять разрыв, если интерполяция явно не предусмотрена.
- Среднее или baseline не публикуется, пока нет полного требуемого окна без missing-значений.

## Формулы аналитики

### Тренировочный объём

Для каждого завершённого рабочего или drop-подхода с положительным внешним весом:

```text
volume = weight_kg * reps
```

В итог не входят разминки, незавершённые подходы, собственный вес, отсутствующий/неположительный вес и неположительное число повторений. Общий объём допустим как показатель нагрузки, но не как сравнение абсолютной силы разных упражнений.

### Estimated 1RM

Для положительного веса и 1–12 повторений используется формула Epley:

```text
e1RM = weight_kg * (1 + reps / 30)
```

За пределами этого диапазона значение считается missing. Сравнение выполняется только внутри одного упражнения.

### Выполнение плана

```text
adherence = finished_scheduled / eligible_scheduled * 100%
```

Явно исключённые сессии и отмены со статусом `excused` не входят ни в числитель, ни в знаменатель. При нулевом знаменателе результат missing, а не `0%`.

### Скользящие средние и baseline

Скользящее среднее появляется только после полного окна и становится missing, если внутри окна отсутствует хотя бы одна точка. Для веса используется окно 7 дней; для HRV, RHR и сна могут показываться 7- и 28-дневные окна по тем же правилам.

### Корреляции

Pearson correlation считается только по парам, где присутствуют оба значения. Ответ содержит коэффициент, фактический размер выборки и флаг недостаточной выборки при `n < 7`. При менее чем двух парах или нулевой вариативности одной серии коэффициент missing. Корреляция описательная и не доказывает причинность.

## Импорт CSV и JSON

Поддерживаемые типы данных:

- тренировки;
- подходы;
- восстановление;
- сон;
- дневные итоги питания;
- измерения тела.

Рабочий процесс импорта:

1. Выбрать тип и источник данных.
2. Загрузить CSV или JSON.
3. Просмотреть распознанные строки и сопоставить поля.
4. Исправить ошибки валидации и проверить найденные дубликаты.
5. Явно подтвердить выполнение.
6. Сверить итоговый отчёт: imported, skipped и failed rows.

Preview ничего не записывает и не должен показываться как успешный импорт. При наличии стабильного `external_id` повторный импорт идемпотентен в пределах владельца, источника и типа данных. Без `external_id` автоматическое распознавание дубликатов ограничено, поэтому повторное выполнение требует ручной проверки preview.

Control Center не заявляет фоновую синхронизацию WHOOP или FatSecret: source
adapters принимают поддерживаемые экспортные файлы, а FatSecret backfill —
отдельная operator-команда. Наличие OAuth-интеграции у Telegram-бота не означает
постоянный sync. UI не должен показывать `Connected`, пока соответствующий live
adapter действительно не настроен и не проверен.

## Production-топология

Целевая схема — Caddy с TLS перед отдельными контейнерами Next frontend и Go API; PostgreSQL остаётся во внутренней сети и не публикуется наружу. Caddy должен отдавать UI и направлять `/api/v1/*` в Go на одном origin, чтобы корректно работали session cookie и CSRF-проверка заголовка.

Перед вводом в эксплуатацию необходимо отдельно проверить production-сборку `web/`, контейнер frontend, Caddy routes, HTTPS/cookie flags, миграции на резервной копии, health checks и rollback. Существующие compose/Caddy-файлы сами по себе не являются подтверждением, что эта схема уже применена.

## Экспорт и удаление

Полный экспорт содержит чувствительные данные о здоровье и тренировках. Храните его как резервную копию с теми же ограничениями доступа, что и базу данных, и не отправляйте в публичные хранилища.

Удаление данных должно быть owner-scoped и требовать явного подтверждения. Перед массовым удалением сделайте и проверьте резервную копию; не считайте UI-confirmation заменой backup/restore-процедуре.

## Известные ограничения

- Только один владелец; нет multi-user RBAC, ролей и делегированного доступа.
- Максимальный аналитический диапазон — 366 календарных дней.
- WHOOP ограничен file import; FatSecret дополнительно имеет ручной лицензируемый backfill, но фоновой live-синхронизации нет.
- Строгая идемпотентность импорта гарантируется только при стабильном `external_id`.
- Missing-окна уменьшают число доступных средних и корреляционных пар; маленькая выборка не трактуется как достоверный вывод.
- Demo seed не является production-данными.
- Production-контейнер, Caddy routing и реальная browser-сессия требуют отдельной post-deploy проверки.
