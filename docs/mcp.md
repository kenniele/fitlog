# FitLog MCP для ChatGPT и ChatGPT Work

FitLog предоставляет один HTTP-адрес `/mcp` с инструментами чтения и добавления
записей. Telegram-команды, CLI, веб-интерфейс, провайдерская синхронизация и
существующие REST-маршруты продолжают работать. MCP включается отдельно.

## Архитектура и принятые решения

`internal/mcpserver` переводит типизированные аргументы MCP в вызовы
`controlcenter.Service`. Сервис использует прежний PostgreSQL-репозиторий и
те же таблицы, что веб и Telegram. Внутренних HTTP-запросов к собственному REST API,
отдельной копии журнала и дублирования SQL для фитнес-данных нет. Парсеры дат,
пагинации и фильтров выделены в общие функции, используемые обоими транспортами.

Транспорт — stateless Streamable HTTP из официального `modelcontextprotocol/go-sdk`
(закреплена версия `v1.6.0`; тестируется согласование протокола `2025-11-25`).
Обработчики возвращают JSON в `structuredContent` и текстовый JSON для клиентов,
которым нужен `content`. JSON-RPC, initialize, schemas и tools/list обслуживает SDK.

`internal/mcpauth` отвечает за OAuth для одного заранее зарегистрированного
клиента. Он отделён от WHOOP/FatSecret OAuth и от dashboard-cookie. Авторизация
MCP не разрешает ИИ читать ключи, переключать пользователя или менять настройки
провайдеров. Владелец совпадает с `Config.DashboardOwner()`: явно заданный
`FITLOG_DASHBOARD_OWNER_ID`, иначе первый `TELEGRAM_ALLOWED_USER_IDS`.
Сохранённый в Settings часовой пояс перечитывается при каждом вызове инструмента.

Для личной установки это небольшой дополнительный адаптер к существующему
приложению. Существующий `controlcenter.Store` остаётся крупным интерфейсом, а
валидация записей частично живёт в репозитории. При переходе к нескольким
пользователям стоит выделить сервисы тренировок/здоровья и заменить авторизацию
на полноценный identity provider. Для текущей задачи такая перестройка всего
FitLog не требуется.

## Инструменты

Чтение доступно со scope `fitlog:read`:

- `get_context` — локальное время, часовой пояс, цели питания/сна, источники и
  последнее время синхронизации. Первый вызов перед анализом относительных дат.
- `get_overview` — общая сводка и дневные значения, при необходимости сравнение
  с предыдущим периодом такой же длины.
- `get_analytics` — `training`, `recovery`, `nutrition`, `body`, `correlations`.
  Поддерживает фильтры упражнения, плана, шаблона, статуса и типа дня.
- `list_workouts`, `get_workout` — тренировки вместе с упражнениями и подходами;
  `status=active` показывает текущие, `scheduled` — запланированные.
- `list_plans`, `get_plan` — планы, шаблоны и предписания упражнений.
- `search_exercises` — поиск существующих упражнений и их ID.
- `list_nutrition`, `list_sleep`, `list_recovery`, `list_body_measurements` —
  исходные записи по периоду, включая источник и доступные подробности InBody.

Добавление записей требует одновременно `FITLOG_MCP_ALLOW_WRITES=true` и
выданного при OAuth scope `fitlog:write`:

- `log_workout` — записать уже выполненную тренировку с подходами в историю.
  Все переданные подходы считаются выполненными. Не управляет интерактивной
  тренировкой бота и не публикует сообщения в каналы.
- `create_workout_plan` — создать новый план с шаблонами и двойной прогрессией.
  `weight_step_kg` обязателен для каждого упражнения. Существующие планы сохраняются.
- `log_nutrition` — добавить ручные **итоги дня**, а не отдельный приём пищи.
  Сначала проверь записи этого дня: повторные итоги с другим `request_id`
  являются отдельными записями. Этот инструмент не пишет в FatSecret.
- `log_body_measurement` — добавить вес, жир, мышечную массу или обхват талии.
  Неизвестные показатели нужно опустить.

Все четыре инструмента записи требуют уникальный `request_id` длиной 8–128
символов. Он сохраняется как `external_id=mcp:<request_id>` с `source=manual`.
Повтор той же операции с тем же ID отклоняется существующим уникальным индексом,
а не создаёт дубликат. Успешная запись возвращает `id`, `resource`, `source` и
`external_id`; подробности доступны инструментами чтения.
После неопределённого результата сначала проверь журнал;
не генерируй новый ID для автоматического повтора. Это защита от повторной
записи, а не обещание вернуть первоначальный успешный ответ.

Инструменты не предоставляют SQL, удаления, публикации в Telegram, обновления
OAuth-провайдеров или массовой перезаписи существующих записей. Запись получает
`readOnlyHint=false`, чтение — `true`; клиент может запрашивать подтверждение
записи. Аннотации не заменяют серверную проверку scope.

## Семантика данных и ограничения

- Даты `from`/`to` включительные, задаются вместе и используют часовой пояс
  владельца. Максимум 366 дней. Сводка по умолчанию содержит последние 30 дат,
  включая текущую. Списки без периода читают всю историю постранично.
- По умолчанию страница содержит 25 записей, максимум — 100. Результат содержит
  `items`, `total`, `page`, `page_size`; при необходимости запрашивай следующие страницы.
- В тренировках `date_basis=actual` использует фактическую дату, `calendar` —
  запланированную. У списков питания/сна/замеров свои календарные даты.
- `null` означает отсутствие значения, а не ноль. В подходах `weight_kg=null`
  означает собственный вес, внешнее отягощение должно быть положительным.
- MCP читает сохранённые данные. Успешный вызов не означает, что WHOOP/FatSecret
  уже обновили сегодняшний день. Смотри `sources` и `last_synced_at`.
- Единицы отражены в именах полей: kg, g, kcal, ml, seconds, ms.
- Нужны измеренные значения; корреляции не доказывают причинность.
- Тело HTTP-запроса ограничено 1 MiB, данные ответа — 2 MiB, выполнение tool —
  30 сек. При слишком большом ответе уменьши период или размер страницы.
- Ошибки валидации возвращаются как MCP `isError` с сообщением и полями;
  внутренние ошибки не раскрывают SQL/секреты клиенту.

## Настройка сервера

1. Примени миграции стандартной командой `fitlog migrate`/`make migrate-up` при
   развёртывании. Миграция `00013_mcp_oauth.sql` добавляет отдельную таблицу
   OAuth-grants; фитнес-таблицы не изменяет.
2. Сгенерируй **два разных** секрета, например дважды выполнив
   `openssl rand -hex 32`. Не публикуй их в репозитории или чате.
3. Настрой окружение приложения:

```dotenv
PUBLIC_BASE_URL=https://your-fitlog.example
FITLOG_MCP_ENABLED=true
FITLOG_MCP_ALLOW_WRITES=false
FITLOG_MCP_CLIENT_ID=fitlog-chatgpt
FITLOG_MCP_CLIENT_SECRET=<первый случайный секрет>
FITLOG_MCP_LOGIN_TOKEN=<второй случайный секрет>
FITLOG_MCP_REDIRECT_URIS=https://chatgpt.com/connector_platform_oauth_redirect
```

Сервер публикует RFC 9207 issuer metadata и возвращает `iss` в OAuth-редиректе,
что позволяет ChatGPT использовать указанный стабильный callback. Всё равно
сверь **точный** callback в настройках созданного MCP-подключения: если интерфейс
показывает другой адрес, используй именно его. Несколько разрешённых callback
задаются через запятую, без wildcard и без пробелов. Для другого клиента также
нужен его точный HTTPS callback. Не добавляй произвольные адреса.

`FITLOG_MCP_CLIENT_SECRET` вводится в OAuth-настройках подключения ChatGPT.
`FITLOG_MCP_LOGIN_TOKEN` вводится только на странице разрешения доступа **FitLog**.
Dashboard token, ключ шифрования и токены WHOOP/FatSecret для этого не нужны.

4. Добавь маршруты в реальный Caddyfile по обновлённому
   `deployments/Caddyfile.example`: `/mcp`, `/oauth/mcp/*` и три указанных там
   `/.well-known/oauth-*` адреса должны идти в `app:8080`, а не в Next.js.
   Реальный Caddyfile не хранится в Git и может содержать другие проекты;
   обновление шаблона само по себе не меняет production-маршрутизацию.
5. Пересоздай приложение со свежим окружением и применённой миграцией обычным
   способом развёртывания проекта. Установка MCP не требует отдельного процесса
   или контейнера. При `FITLOG_MCP_ENABLED=false` его маршруты отсутствуют.

Проверка публичной маршрутизации без секретов:

```bash
curl -i https://your-fitlog.example/mcp
# Ожидается 401 с WWW-Authenticate и resource_metadata.
curl -fsS https://your-fitlog.example/.well-known/oauth-protected-resource/mcp
curl -fsS https://your-fitlog.example/.well-known/oauth-authorization-server
```

## Подключение ChatGPT / Work

Включи Developer mode, создай пользовательское MCP-подключение в разделе
Plugins/Apps и укажи:

- URL: `https://your-fitlog.example/mcp`.
- Authentication: OAuth; используй заранее заданные client credentials.
- Client ID: значение `FITLOG_MCP_CLIENT_ID`.
- Client secret: значение `FITLOG_MCP_CLIENT_SECRET`.

Пройди страницу разрешения FitLog с `FITLOG_MCP_LOGIN_TOKEN` и выбери
подключение в чате/задаче Work. Доступность настройки зависит от разрешений
аккаунта/рабочего пространства. Автоматическая регистрация DCR и CIMD в этой
версии не реализованы: не оставляй поля клиента пустыми.

После включения `FITLOG_MCP_ALLOW_WRITES=true` повторно авторизуй подключение
со scope `fitlog:write` и обнови список инструментов в клиенте. Читающий токен
не получит право записи только из-за изменения конфигурации. При отключении
записи сервер немедленно перестаёт предоставлять её инструменты после перезапуска.

Примеры запросов:

> Через FitLog сравни последние четыре недели с предыдущими: тренировки,
> питание, сон и восстановление. Сначала проверь свежесть источников.

> Найди жим лёжа и покажи, как изменились веса, повторения и RIR за 90 дней.

> Предложи план на три тренировки в неделю на основе моей истории.
> Покажи его мне перед сохранением.

> Запиши сегодняшний вес 80,2 кг, остальные показатели неизвестны.

## OAuth и отзыв доступа

Используются authorization code + PKCE S256, точное совпадение redirect URI,
CSRF-защита формы с привязкой к параметрам разрешения, проверка audience/resource
и scope. Access token живёт час. `offline_access` позволяет обновлять подключение
до 30 дней от выдачи. Refresh token ротируется; старые code/refresh не принимаются
повторно. Операция обновления токенов атомарна в PostgreSQL. Grants сохраняются
между перезапусками; в таблице лежат только хеши случайных кодов и токенов.

`POST /oauth/mcp/revoke` с OAuth client authentication и полем `token` отзывает
соответствующий grant целиком. Изменение login token или client secret отзывает
все прежние grants этого подключения; смена владельца, callback-списка, client ID
или публичного origin также делает их недействительными. Удаление приложения
из ChatGPT не следует считать гарантированным отзывом на стороне FitLog, если
клиент не вызвал revocation endpoint.

## Проверки

Без PostgreSQL:

```bash
go test -race -count=1 ./internal/mcpserver ./internal/mcpauth ./internal/config ./internal/server ./internal/controlcenter ./cmd/fitlog
go vet ./cmd/... ./internal/... ./migrations/...
```

В изолированной, уже мигрированной тестовой базе:

```bash
TEST_DATABASE_URL='postgres://.../fitlog_test?sslmode=disable' \
  go test -race -tags=integration ./internal/mcpauth
```

Интеграционный тест проверяет одноразовый конкурентный обмен OAuth-кода,
сохранение grants между экземплярами сервера, срок действия, четыре записи через
HTTP MCP, повторные request IDs и недоступность записи другому владельцу.
Он не обращается к настоящим WHOOP, FatSecret или Telegram. Обычная команда
`make test` сохраняется; тесты, использующие `httptest.NewServer`, требуют
разрешения открывать локальные сокеты.
